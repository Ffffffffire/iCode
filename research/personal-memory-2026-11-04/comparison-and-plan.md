# 个性化记忆横向比较与下一阶段方案

核实日期：2026-11-04。本文供 iCode 个性化记忆的产品取舍与后续实现使用，阅读入口是本文件；两份配套证据记录位于同目录。本文依据官方文档、固定提交源码及当前 iCode 工作树，不是七款产品的运行效果或性能排行榜。本轮只形成研究与方案，没有修改功能实现。

**建议继续沿用“主 Agent 按需写入、本地有界召回、来源可查、修订可控”的路线，把下一阶段重点放在适用性、证据回读和纠偏闭环。** 对比没有提供足够证据支持把每回合后台提炼、向量数据库或知识图谱设为必选项。成熟程度应由正确保存、适时使用、及时纠正这些行为证明。

方案的第一性原则是：**个人记忆保存的是未来做判断时仍有用、带适用条件、能够被新证据修正的依据。** 历史记录负责说明发生过什么；记忆负责指出哪些经历仍应影响现在；技能负责怎样重复完成一类工作；规则与审批负责必须遵守什么。它们可以关联，但不应相互替代。

## 3. 对记忆设计的五个实质性认识

**第一，少量常用约定与大量条件化经验需要不同的读取方式。** Claude 的索引、Hermes 的小容量常驻事实及技能分工，都在控制每次调用的负担。对我们，“先给结论，再给必要证据”可能是长期协作约定；“技术 PPT 倾向高密度图形”只适合某些产物；“上次为什么没有采用轨迹 IR”需要回到历史依据。三者全部交给同一条关键词查询，必然在漏召回与干扰之间反复调整。

这不要求建立三套数据库。可以保留现有唯一记忆库，让很少量、用户确认的常用约定获得固定读取入口；条件化记忆继续走有界检索；原始经历保留在已有会话存储，需要时通过来源定位。对会变的事实，保存重新核实的入口通常比长期复制旧值更可靠。

**第二，语义相似只解决“可能有关”，不能解决“现在应该照做”。** 例如“为远距离投影做三页极简 PPT”与“高密度技术 PPT 偏好”非常相似，但应当触发例外。当前任务、记忆适用条件、失效条件必须一起参与使用判断。向量或更多别名不能替代这一层，反而可能更稳定地找到不该执行的旧偏好。

Hermes 的搜索代码还揭示另一类问题：自动任务积累大量重复词汇，会挤掉真实用户经历；它通过会话谱系去重、来源降权及有界展开处理。我们将来接入历史检索时，首先要区分用户原话、模型摘要、工具输出与子代理记录；同一原话被总结多次，不能算多份独立证据。[源码](https://github.com/NousResearch/hermes-agent/blob/9302ba9e212c63ba24cdf1f47f26b47bcd3b042e/tools/session_search_tool.py)

**第三，记忆质量更多取决于可逆纠偏，而不是无限加强抽取。** 条件遗漏、主语变化、从偏好升级为强制规则，都会让一条流畅的记忆产生负作用。原话能核对，只证明这句话出现过，不证明润色后的全部含义都受到支持。应让用户容易表达“这次例外”“长期变了”“原先记错了”，分别产生临时停用、版本修订或撤回，不把三者统一当作覆盖旧文本。

Hermes 的局部 patch、最终容量校验和审批时绑定原目标，说明合并首先是一个正确修改对象的事务。现有 iCode 的 ID 与 revision 已经是合适基础，不必换成字符串匹配；应进一步把多条合并也纳入同一原子操作，保留各自仍成立的条件与来源。[存储实现](https://github.com/NousResearch/hermes-agent/blob/9302ba9e212c63ba24cdf1f47f26b47bcd3b042e/tools/memory_tool_store.py)

**第四，压缩提供分析机会，不提供长期有效性的保证。** Pi 区分压缩前、已保存和失败事件，DeepSeek Harness 用保留原事件的投影视图表示压缩，Hermes checkpoint 区分原始证据与旧摘要。共同启发是：候选来自原始证据，成功提交后才能发布，摘要本身不是新的独立证据。我们当前复用已有压缩请求、最多生成少量待确认候选的方向应保留。[Pi 扩展契约](https://github.com/earendil-works/pi/blob/676af1d777ef6f04b6bc8daf4cf3b9b1799cff4d/packages/coding-agent/docs/extensions.md) · [DSH 会话日志](https://github.com/deepseek-ai/deepseek-harness/blob/8bd073392eef6f54e921a093b95076248eb08cbb/packages/core/session/README.md) · [Hermes 压缩证据](https://github.com/NousResearch/hermes-agent/blob/9302ba9e212c63ba24cdf1f47f26b47bcd3b042e/agent/conversation_compression.py)

**第五，记忆可见性应该帮助用户校准，而不是宣传记忆存在。** “向模型提供了两条记忆”“模型表示据此调整方案”“用户指出其中一条不适合本次”是三种不同事件。当前资料不足以确认这些产品都具备可靠的因果效果归因。我们也不应根据一句泛泛的肯定给记忆自动加分，或者因长期未使用就删掉低频关键经验。TUI 更有价值的入口是查看依据、只停用本次、修正长期记忆，而不是不断弹出召回数量。

## 5. 优化方案：在现有边界内完成五项改进

### 5.1 读取区分常用约定、条件化经验和历史依据

仍使用现有条目与 Store。只有用户明确确认长期、普遍适用的协作约定，才进入小型常用入口；普通 preference 不自动常驻。其余条目保留现有混合检索。用户追问历史原因或当前条目不足以支持判断时，才通过来源定位读取小段原文。

检索顺序：当前会话政策与使用范围 → 活跃状态及明确冲突约束 → ID/标题直达或词项候选 → 条件与当前任务的适用性判断 → 在总预算内提供内容。直接指定 ID 可以用于查看，不代表强迫应用。没有匹配时，主 Agent 可按任务中的决定、机制或约束换一种检索表达；不默认额外调用重排模型。

借鉴 Claude 的短入口时，要先看库的规模：小库无需新增一套目录。只有候选较多时才先返回短条目、按需展开详细来源。自动入口与工具扩展必须共用预算，不能各自 5 条而在同一回合无限累计。保留最多 5 条、6,000 字符作为初始产品约束；低价值结果宁可不补满。

语义向量作为后续可选补充：仅当已有真实用例证明词项、别名和主 Agent 改写仍持续漏召回时引入；缓存必须绑定条目版本和作用域，删除或停用即失效，故障时退回本地检索。本文不指定未验证的 embedding 模型、相似度阈值或效果数字。

### 5.2 写入采用简短且可执行的选择规则

| 当前信号 | 行为 |
| --- | --- |
| 普通任务、一次性格式要求、任务进度 | 不调用记忆写入，不启动额外提炼 |
| 明确“记住、更新”且内容可复用 | 主 Agent 整理为简短依据，检查相关条目，按授权保存或修订 |
| 提炼建议开启，用户直接表达稳定个人偏好 | 在原话支持的范围内保存；不能把本次限制自动升级为长期偏好 |
| 经验需要推断，或适用范围不明确 | 仅生成少量可审核候选；没有足够价值时不生成 |
| 压缩已产生可复用个人内容 | 复用现有摘要调用，保留原话和提交边界，仍走候选审核 |
| 多步骤工作方法 | 当前记忆保留必要的个人选择或条件；方法足够稳定、用户愿意复用时再转为技能 |
| 可从当前代码或系统直接核实的事实 | 优先核实现状；确有跨会话价值时保存定位入口和理由，避免复制易过时值 |

一条优质记忆通常能表述为：“在什么情形下，倾向或避免什么，原因是什么；有什么例外。”只填写有证据支持的部分。完整并不等于每条都必须凑齐原因和例外，润色也不能补写合理但未经用户表达的解释。

### 5.3 更新处理四种情况，合并保证事务正确

同义重复不新增，也不增加证据量；补充信息修订原条目并保留已有条件；暂时例外仅影响本次调用；长期改变产生新版本并停止旧版本参与召回。完成的长期意图可以退出活跃集，其历史依据仍留在会话记录中。

跨条目合并由 Store 接受所有目标 ID 与预期 revision，核对同一作用域、来源及用户授权，生成保留有效条件的结果，再一次提交结果与旧条目退出状态。任何版本冲突都应要求刷新，不能部分执行。只有引入此消费方时才扩展多来源表示，不为“知识图谱”预先增加实体、关系和推理字段。

后台或压缩产生的纠偏建议不能覆盖人工新更正。显式忘记仍走删除语义，暂停仍可恢复；不可把“用户这次没采用”解释为全局错误。

### 5.4 把 Buddy 与工具摘要变成纠偏入口

复用现有工具折叠行和 Buddy 展开面板。默认只显示可证实的事件，如“参考了 2 条”“新增 1 条待确认”；详情关联本次调用的条目与版本，提供“查看依据”“这次不用”“长期改了”。这些是拟议文案与行为，不代表已交付。

“这次不用”在当前任务内抑制该条目，下一次推理看到抑制结果；“长期改了”带原版本发起修订；“查看依据”定位原话。“模型采用”只能记录为模型的声明，不能显示成效果已验证。用户的否定若不能明确定位条目，只暂存本次反馈或继续澄清，不能批量降权。

事件复用既有 EventBus 与轨迹身份，界面可以保留完整操作回执，模型只收到当前任务需要的信息。避免为了显示功能存在而反复注入解释性长文本，也不增设后台效果评分模型。

### 5.5 分离当前会话的读取和贡献许可，预留共享知识入口

现有全局 auto/manual/off 与 capture 已有基础，进一步补会话覆盖：用户可以沿用默认、只使用不贡献、或本次关闭。会话限制同时约束工具写入和压缩候选；不能因为工具没有写，就由压缩侧绕过限制。实现上应复用宿主会话设置和统一有效政策，不在不同入口各写一份判断。

项目私有记忆仍属于用户；同一仓库工作树共享只解决使用范围。组织级记忆应是经过授权发布、有共同适用条件、维护者与撤销机制的知识资产，不能把个人库换个 scope 后直接共享。Session Analyst 可以离线形成候选，个人记忆可提供获准共享的线索；团队审核后进入已有文档、规则或技能入口。组织硬约束由权限、审批、Hook 或检查执行，召回只提供背景和解释。

## 6. 实施顺序与验收

| 阶段 | 优先交付 | 主要改动位置 | 能证明完成的结果 |
| --- | --- | --- | --- |
| P0：先让错误容易被发现和纠正 | 逐回合条目版本回执；“这次不用/长期改了”；适用性与来源回读；保持现有写入门槛 | runtime、现有事件/轨迹、Buddy/工具摘要、会话读取服务 | 同一偏好在正常与例外场景产生不同动作；用户一次操作能止住本次干扰或修订长期内容 |
| P1：补召回与维护完整性 | 少量常用约定入口；项目身份；多条原子合并；会话读写覆盖 | 现有 schema/Store/retrieval、工作区构建、会话设置 | worktree 正确共享且不同项目隔离；并发更正不丢失；合并失败不留下半完成状态；只读会话无新候选 |
| P2：有证据再扩大能力 | 有界历史发现；可选语义补充；用户触发的整理；组织候选提升 | 会话/轨迹索引、现有检索扩展点、Session Analyst 接口 | 在固定真实漏召回集上新增机制确有收益，成本可解释；没有扩大来源范围或自动共享个人内容 |

P0 不需要新数据库、独立 provider、每回合反思或通用知识图谱。P2 的整理只在用户请求、明确冲突或容量压力下形成可审查的合并、失效或技能建议；关联生成的是待验证假设，不自动晋升为更高可信知识。这也是对早期 dream 设想更可控的实现方式。

后续测试应沿用户真实入口进行，以下为待执行的验收场景，不是本轮测试结果：

| 场景 | 必须观察的行为 |
| --- | --- |
| “修复这个 API 报错” | 无记忆写入与额外提炼模型调用；有相关现成记忆时可以读取 |
| “我更喜欢技术汇报图形多、信息密度高，帮我记住” | 保存成功，内容保持原范围，不额外发明例外或操作步骤 |
| 新会话用“讲清模型结构的汇报页”表达同类任务 | 有合适召回；记录具体命中、实际模型输入与最终行为，不能只查返回列表 |
| “这次远距离投影，要三页极简” | 当前要求优先；高密度偏好被判为不适用，不自动改掉长期偏好 |
| “这次不用”和“以后都改成低密度” | 前者只抑制本次，后者修订指定版本，下一会话行为相应变化 |
| 同一段原话经多次压缩或批量分析 | 不重复新增，不冒充多次独立确认；压缩失败无成功保存回执 |
| 两个会话同时修改同一条；旧候选稍后启用 | 旧版本不能覆盖新更正；错误明确且内容完整 |
| 合并两条重复经验时发生错误 | 要么整批成功，要么全无改变；条件与来源可核查 |
| 同仓库两个 worktree、另一仓库、个人全局偏好 | 项目私有知识只在对应项目共享，个人记忆按其条件跨项目使用 |
| 问“这个结论依据哪次讨论” | 按已授权 source 返回有界原文；不会自动扫描全量历史或引用弃用分支作当前决定 |
| 只使用不贡献的会话发生压缩 | 不写新记忆或候选，仍可按设置读取既有条目 |
| 停用、忘记或外部修订后立即重复查询 | 热缓存不返回已退出或旧版本内容 |
| 500 条上限附近、冷启动、连续热查询、并发更新 | 分别记录墙钟耗时、文件读取/解析、候选数、注入字符和实际模型 token；不预先编造性能结论 |

效果评估以固定的真实场景和明确预期为依据：应召回是否命中、不应应用是否避免、保存与更正是否成立、是否新增模型请求、预算是否遵守。只有得到这些结果后，再决定扩大检索机制；工具调用次数和产物数量本身不证明价值。
