# 个性化记忆检索：成熟机制的复用边界与近期改进

核验日期：2026-11-10。面向维护 iCode 个性化记忆召回、评审检索改动的开发者；本文件通过仓库 `research/` 目录发现，不参与运行时加载。目标是确定现有漏召回应修在哪一层，以及何时才有证据引入全文或向量后端。验证依据为限定范围的本地源码、官方文档、固定版本的作者源码和一次内存 SQLite 探针；不包含用户历史会话、真实个人记忆库或跨产品效果评测。

**结论：优先复用成熟检索的处理顺序和分词方法，当前没有证据要求更换后端。** 已发现的两个具体风险分别是“不可用条目占满候选窗口”和“代码标识符没有拆成自然语言词项”。这两类问题换成向量库或加重排仍可能存在。SQLite FTS5 是后续词项后端的优先候选；QMD、LanceDB 值得借鉴组合检索，但完整引入前必须证明存在当前词项检索无法解决的语义缺口，并接受部署、模型和索引维护成本。

## 1. 当前系统已经具备什么，缺口在哪里

**本地代码确认，指调研开始时的实现。** [retrieval.py](../../src/chrys/service/personal_memory/retrieval.py) 已有字段加权的 BM25F 式检索、直接 ID、精确标题、领域别名、中文二元词、有限英文拼写容错、按工作区的索引视图和有界查询缓存；派生索引可以从 JSON 权威库重建。它不是每次遍历全部正文的简单字符串搜索。[store.py](../../src/chrys/service/personal_memory/store.py) 负责状态、范围、证据版本、待办状态、去重及注入预算：单次最多 5 条、6,000 字符，整个回合最多 15 条、18,000 字符；L0—L3 应继续共用这些约束。

调研开始时，`_select()` 先取检索器最多 32 条候选，再排除证据不再有效、已完成或稍后处理的待办、本轮排除项和已提供版本。因此，高分但不可用的条目可能占完窗口，让窗口以外的可用条目无法进入结果。另一个风险是词法正则保留 `retry_policy.py` 这样的完整词，而自然语言条件可能写成 `retry policy`；仅有子串相似并不能保证两边形成相同词项。本轮已经在公开入口复现这两类漏召回，再修复并通过对应回归；实现范围见下文。[候选生成](../../src/chrys/service/personal_memory/retrieval.py) · [选择与预算](../../src/chrys/service/personal_memory/store.py)

### 本轮落地及其证据边界

- **预过滤**：先确定可用 ID 集合，再建立评分视图、计算门槛和截断候选。仍使用同一个增量词项索引；工作区和可用集合共同限定有界视图缓存。40 条高分失效来源记录、40 条已完成／取消／暂缓待办均不能挡住可用的低分目标；本轮排除在下一回合恢复，缓存不跨工作区串用。[公开 Store 用例](../../tests/service/personal_memory/test_recall_eligibility.py)
- **双向词界分析**：记忆字段和各层查询使用相同规则，保留完整标识符，补充 snake_case、CamelCase 和已识别文件名的组成词。大小写边界在 casefold 之前识别，缓存区分原始词界不同的查询；`C++`、`C#`、`.NET` 和已有领域别名保留原意。另补测并修复 `PowerPoint.md` 被错误拆出普通词 `power` 的误召回；产品与模型名称不会仅因连字符被任意拆开。普通正文走无标识符快速路径，避免逐词重复分析。[实际工具／Store 用例](../../tests/service/personal_memory/test_layered_recall.py)
- **分层贯通**：真实引擎的模型客户端边界检查 L0/L1 首份请求、L2 动作后的请求、L3 查询后的请求，核对实际文件产物和同一份版本回执。模型客户端是可控外部替身，证明消息与工具链，不能证明真实模型会自主选择正确的查询时机。[引擎用例](../../tests/orchestration/engine/test_memory_action_recall.py)
- **可证伪评测**：原有脚本曾只接受 L3 标签而不执行主动查询，也只检查指定的禁止项。本轮加入真正的 `recall_memory` 调用、严格额外项检查和工具错误判定。88 个样例中新增 24 个严格标注场景；旧 64 例保留部分标注，未标注项单独报告，因此不计算或声称整体精确率。[评测和运行指南](../../tests/service/personal_memory/README.md)

本轮没有增加依赖、嵌入模型、索引数据库或另一套记忆权威库。5,000 条较长合成记忆的本机测量显示：热查询中位数约 9–11 ms、未缓存查询约 103–106 ms，冷建索引约 1–2 秒；携带每条 5 份修订的旧库首次落盘导入约 23 秒。后者属于迁移成本，不能并入正常查询后声称所有操作均为毫秒级。样本量每种状态 10 次，冷实例 5 次，操作系统文件缓存未清空；不构成跨平台 SLO。性能脚本见 [benchmark_personal_memory.py](../../scripts/benchmark_personal_memory.py)。

| 责任 | 要回答的问题 | 近期处理原则 |
|---|---|---|
| 范围、生命周期、证据硬过滤 | 这条记忆现在允许用吗？ | 确定可用集合，再截断候选；更新、停用和遗忘立即影响可用性 |
| 词项或语义检索 | 哪些可用条目值得检查？ | 用一致的分析器构建文档和查询词项，保留直接定位与拒绝无关结果的能力 |
| 适用性判断与上下文装配 | 这次是否应按它行动？ | 核对条件、例外和当前用户要求；按版本去重，遵守回合预算，记录实际提供内容 |

**支持性推论。** Azure 官方说明，先取 Top-k 再过滤可能产生假阴性，严格后过滤对选择性强的条件尤其明显。其文档针对分片 HNSW，并不是当前本地算法的性能说明；可复用的是“有限候选窗口之前处理硬资格约束”这一原则。不可用项的分数再高，也不应挤占可用项的候选位置。[Azure：向量检索过滤时机](https://learn.microsoft.com/en-us/azure/search/vector-search-filters)

## 2. 本轮改造采用的成熟规则

### 可用集合先于候选截断

将状态、项目范围、证据版本、已完成或暂缓待办、本轮排除和已提供版本纳入本次检索的候选资格，再计算或截取结果。具体实现应复用现有索引，不为每次不同的动态排除集合重建索引，也不修改记忆权威库。缓存可以复用词项分析和静态评分，但缓存命中不能绕过当前资格检查。

验收应通过公开 `Store.recall`：构造超过候选窗口数量的高分不可用条目，另放一个相关且可用的条目，要求后者仍能召回；同时验证过期证据、其他项目、已完成或暂缓待办、已提供版本均不会重新进入自动注入。只测私有过滤函数无法证明这条完整路径正确。

### 代码标识符保留原词，同时提取组成词

**官方方法确认。** Lucene 的 `WordDelimiterGraphFilter` 按标点、大小写和字母数字边界拆分标识符；Elastic 提供保留原词、保护词和字符类型配置。官方也提醒分析器顺序会影响拆词：前置 tokenizer 若先移除标点，后面的过滤器已无法正确利用它。这里可以借鉴词界规则，无需引入 Java 或 Elasticsearch。[Lucene：WordDelimiterGraphFilter](https://lucene.apache.org/core/10_0_0/analysis/common/org/apache/lucene/analysis/miscellaneous/WordDelimiterGraphFilter.html) · [Elastic：word_delimiter_graph](https://www.elastic.co/docs/reference/text-analysis/analysis-word-delimiter-graph-tokenfilter)

**本轮采用的轻量规则。** 在索引和查询两侧共享词界与别名分析，覆盖以下行为；没有照搬完整 token graph 或全部语言学处理：

| 输入 | 应保留的辨识能力 | 应补充的匹配能力 |
|---|---|---|
| `retry_policy.py` | 完整标识符和已有直接匹配 | `retry`、`policy`，使工具参数能找到自然语言条件 |
| `RetryPolicy`、`HTTPServer` | 完整原词 | 先识别大小写词界，再 casefold；避免大小写信息先丢失 |
| `.NET`、`C++`、`C#` | 三者各自的技术含义 | 不将它们统一退化为普通 `net` 或 `c` |
| 文件路径与带标点名称 | 原始路径或名称的精确性 | 仅增加有意义的组成词，不让通用扩展名主导匹配 |

验收应把真实的编辑或命令参数送入 L2 行动召回，而不只断言 tokenizer 输出；同时保留 `.NET`、`C++`、`C#` 的负例，以及普通网页任务不会因一个泛词自动引用 PPT 偏好的负例。完整 Lucene token graph 解决的是位置、短语等更广问题，当前不需要照搬它的全部机制。

## 3. SQLite FTS5：可选词项后端，不能原样替换

**官方能力与限制。** `unicode61` 将连续 Unicode 字母数字等字符归为词，不提供中文词语切分；`trigram` 的全文查询不足三个 Unicode 字符时不会匹配。因此，原始中文直接入库会损失当前二元词能力。FTS5 `bm25()` 支持列权重，但分数越小越好，其长度归一化也不等同于当前实现；原门槛不能直接迁移。external-content 索引由应用负责一致性，SQLite trigger 不会同步另一份 JSON 文件。[SQLite：分词](https://www.sqlite.org/fts5.html#tokenizers) · [trigram](https://www.sqlite.org/fts5.html#the_trigram_tokenizer) · [bm25](https://www.sqlite.org/fts5.html#the_bm25_function) · [外部内容一致性](https://www.sqlite.org/fts5.html#external_content_table_pitfalls)

**本机探针，已执行。** 使用 `uv run python -`、标准库 `sqlite3` 和 `:memory:` 数据库，未访问产品记忆库，也未写磁盘。环境为 Python 3.14.8、SQLite 3.53.1；三次均成功创建 FTS5 表：

| 建表方式与入库内容 | `MATCH` 查询 | 返回行数 |
|---|---|---:|
| `tokenize='unicode61'`；`缓存系统` | `缓存` | 0 |
| `tokenize='trigram'`；`缓存系统` | `缓存` | 0 |
| 默认 FTS5；预切为 `缓存 存系 系统` | `缓存` | 1 |

这只证明当前 Windows 环境的可用性和这个分词边界，不是跨平台保证或性能基准。预切词方案也不能因此宣称拥有原文短语、位置和 snippet 的完整语义。

**若以后采用，建议仍让 JSON 保持权威，FTS5 仅为可丢弃的派生索引。** 沿用已测试的中英文词项分析器，保存索引代际、分析规则版本及条目 ID/内容版本的对应关系；事务内生成一致的索引快照。启动或查询发现代际不一致时重建或回退现有检索，不把旧缓存结果当权威。损坏重建、删除后不可检索、修订立即可见、多窗口读写和目标平台 FTS5 可用性，均须在引入前有测试。SQLite 提供 `rebuild`、`integrity-check` 等维护命令，但 JSON 与索引之间的协议仍由本项目负责。[SQLite：rebuild](https://www.sqlite.org/fts5.html#the_rebuild_command) · [integrity-check](https://www.sqlite.org/fts5.html#the_integrity_check_command)

## 4. QMD：借鉴分阶段检索，不直接搬入整套运行时

QMD 本轮核验固定到 [`86d2365d17fc682e491c2c53d1e4a884aee8682a`](https://github.com/tobi/qmd/commit/86d2365d17fc682e491c2c53d1e4a884aee8682a)，避免以变动的 README 代替源码。

**源码确认。** 当前 `hybridQuery()` 先做 FTS 探查；未指定 `intent`、词项信号强且与第二名拉开差距时跳过模型查询扩写。后续可结合原查询和扩写的 FTS/向量列表，做带权 RRF、截取候选，再选取文档片段重排。默认重排候选上限为 40；这只是该项目配置，不能据此推出本项目最佳窗口。值得借鉴的是“已有明确证据时减少昂贵步骤”和“只重排有界候选片段”。[检索编排](https://github.com/tobi/qmd/blob/86d2365d17fc682e491c2c53d1e4a884aee8682a/src/store.ts#L6264) · [RRF](https://github.com/tobi/qmd/blob/86d2365d17fc682e491c2c53d1e4a884aee8682a/src/store.ts#L5371)

**部署成本确认。** 该版本是 MIT 许可的 Node 项目，要求 Node ≥22，并依赖 `better-sqlite3`、`sqlite-vec`、`node-llama-cpp` 等；模型层用本地 GGUF 执行嵌入、扩写和重排。因此它不是能直接导入当前 Python 服务的无依赖库，也不能把“本地检索”理解为没有模型加载与推理成本。[包声明](https://github.com/tobi/qmd/blob/86d2365d17fc682e491c2c53d1e4a884aee8682a/package.json) · [模型层](https://github.com/tobi/qmd/blob/86d2365d17fc682e491c2c53d1e4a884aee8682a/src/llm.ts#L279)

**适用判断。** 若未来已有用户选择的较大文档集合，QMD 的 CLI/MCP 集成可以单独评估；个人记忆不应为每个回合自动承担其扩写和重排链路，也不应把个人偏好的启用、修订、版本和效果回执委托给文档搜索服务。本轮没有运行 QMD，不能断言它对用户记忆更准或更快。

## 5. LanceDB：后续语义后端候选，不是现有错误的通用补丁

**官方能力确认。** LanceDB 的 hybrid search 先分别执行 FTS 与向量检索，再合并和重排，默认可使用 RRF；也可显式传入文本与查询向量。自动文本向量化需要配置嵌入模型或服务，不能把数据库安装等同于语义检索已就绪。[LanceDB：Hybrid Search](https://docs.lancedb.com/search/hybrid-search)

当前官方文档已提供 native FTS，不能沿用旧资料认定必须安装 Tantivy。默认英文分析配置不等于中文检索已妥善处理；官方另提供 ICU、Jieba 等分词选择。未索引新增数据默认可以扫描补足，`fast_search()` 则跳过未索引部分，因此索引更新策略会改变可见性。[LanceDB：Full-Text Search](https://docs.lancedb.com/search/full-text-search)

RRF 本身不需要模型；cross-encoder 或托管重排则增加模型运行或服务调用成本。重排只能改变已有候选顺序，无法找回候选集从未包含的目标。[LanceDB：Reranking](https://docs.lancedb.com/reranking)

**适用判断。** 真正的无共同词项语义漏召回持续出现、且轻量别名或词界修复无法解决时，才比较 LanceDB 与其他后端。嵌入模型版本、模型文件或服务依赖、增量索引、删除传播、数据离线可用性及多窗口访问都成为需要维护的产品能力。现阶段只为解决中文短词、文件名拆词或先截断后过滤引入它，收益不足以解释新增成本。

## 6. RRF 可以复用，但不能把召回层级当多路投票

**官方算法确认。** RRF 用各结果列表中的排名融合，不要求原始分数处于同一尺度；列表窗口和排名常数会改变结果。Azure 还说明，RRF 得分范围随融合查询数变化，不能把它当相关概率，也不能照搬 BM25 的阈值。[Elastic：RRF](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion) · [Azure：混合检索评分](https://learn.microsoft.com/en-us/azure/search/hybrid-search-ranking)

**本地推论。** L0—L3 是“何时取记忆”的策略层；ID、标题、别名、拼写则多数仍属于同一词项证据体系。将每个层级或词法变体都单独作为 RRF 列表，会让重复识别同一证据得到多次投票，并不自动增加独立信息。后续若出现词项与向量这类互补候选列表，可以用无模型的 RRF 合并，再按条目 ID/版本去重；精确 ID 和明确标题仍需保护，不能被多个宽泛语义命中冲掉。无关查询仍应允许返回空结果。

当前自动召回的“保留最强词项分数一定比例”属于现有分数体系的门控，不能移植成同一比例的 RRF 门控。任何融合改动都需要同时测漏召回和无关注入，不能只看返回条数增加。

## 7. 决策门槛与验证方式

以下门槛是本项目建议，不是已经达成的性能或效果结论。无需先设“达到多少条就必须换库”，而应检查瓶颈的实际来源。

| 观察到的证据 | 下一步 | 仍须保持的约束 |
|---|---|---|
| 词界不一致、候选截断顺序、缓存陈旧导致稳定复现的漏召回 | 先修当前分析器、资格过滤或缓存失效 | 不引入外部模型调用；公开入口回归能证明修复 |
| 隔离查询分析、候选评分、加载和持久化后，确认词项索引 CPU、内存或冷启动构成瓶颈 | 用同一分析器和语料 A/B 比较现有实现与 FTS5 | 新增、修订、停用、遗忘实时可见；重建和跨平台可用 |
| 在词项、别名和标识符已正确处理后，仍有高价值“表达不同但含义相关”的标注漏召回 | 小范围评测向量候选与 RRF | 作用域和证据版本先过滤；记录嵌入、模型加载或调用成本 |
| 相关目标已进入候选，但总被相似而不适用的条目压后 | 先检查适用条件与字段权重，再评估重排 | 不能用重排代替硬过滤；必须验证无关注入是否增加 |

评测语料可先使用公开、合成的明确偏好与项目场景；每个案例标记允许召回 ID、禁止召回 ID，以及预期触发层。标注来自开发者构造时，应称“回归样例”，不能称用户真实收益或人工使用评测。之后需要真实场景时，应单独取得并按许可使用数据，本轮没有读取它们。

应在同一语料、预算、机器与冷暖状态下记录：目标进入候选和实际注入的情况，其他范围或不可用条目的注入数，无关查询的错误注入，以及公开入口延迟和索引更新成本。MRR 只描述预先标注目标的排序；召回命中不等于模型正确采用，更不等于帮助用户。使用效果仍要从已有提供回执、条目版本、明确反馈和后续纠偏中单独判断。
