# 个性化记忆的 Git 演变与清理

以 iCode 功能分支修订 `fe1fd1e8` 为审查基线，沿分支独有提交、三个上游合并及本机可见的 Chrys 前身分支核对。GitHub 的 PR 列表对 `Ffffffffire:codex/personal-memory-tui-20261031` 返回空结果。个性化记忆的产品决策因此以功能分支的提交、代码、测试和研究记录为依据，上游 PR 用来验证平台能力与边界。

长期记忆保存能改变未来判断的经验、约定和意图。来源、适用条件、使用回执和用户反馈分别回答「依据是什么」「何时适用」「提供了什么」「结果如何」。一份数据只有在当前行为还需要据此作决定，或者用户仍需要它来核对和恢复时，才值得继续维护。

## 可核实的上游 PR

- **配置文件仍是一等入口。** `a3b9c198` 严格解析 `memory.files`、`memory.folders`，修复把单个字符串拆成字符列表的问题。这保护的是选定文件的读取。结构化经验的写入、审核与召回有自己的存储和工具契约。[iCode #249](https://github.com/openJiuwen-ai/iCode/pull/249)
- **压缩成为请求前按需提交的整批操作。** `c762541d` 合入了新版压缩调度。个性化记忆通过 `SummaryExtension` 接入已经发生并成功提交的压缩，基于折叠范围内的用户原话生成候选。这个挂钩的去留取决于提交、失败和重试的语义，跟旧提炼超时是两个问题。[iCode #283](https://github.com/openJiuwen-ai/iCode/pull/283)
- **内置 Agent 的提示词跟随包版本。** `b9053ec3` 区分包内提示词与用户设置，防止用户保存配置后一直沿用旧提示词。特性的写入门控仍须由运行时根据用户、来源和记忆状态核验。[iCode #307](https://github.com/openJiuwen-ai/iCode/pull/307)
- **测试需要观察真实挂载与就绪状态。** `debbcb9f` 带入异步测试就绪和页脚刷新修复。功能分支 `fe1fd1e8` 随后调整了记忆面板测试。这里涉及真实的渲染时序，和记忆数据格式的历史兼容分别判断。[iCode #313](https://github.com/openJiuwen-ai/iCode/pull/313)

## 现有设计的去留

| 判断 | 现在承担的职责 | 处理 |
| --- | --- | --- |
| 有意保留的写入边界 | 用户授权控制立即生效。明示稳定偏好可按设置生效，推断经验进入候选。压缩候选需要出处，并在压缩提交后落盘 | 保留授权、证据、修订和审核各自的检查。收敛旧「自动提炼关闭」报错的措辞，使其对应当前的建议开关 |
| 有意保留的召回分工 | 常驻和到期待办、开场匹配、关键行动前补查、主动检索各有入口。相关性先于已提供版本的去重 | 保留 L0–L3、预算和重放。L2 查到可改变动作的依据时才暂缓执行，后续动作照常走审批 |
| 有意保留的审计与恢复 | 回执用于当前回合的交付、反馈匹配和预算。活动日志记录召回与实际反馈，并承担旧修订恢复。目录提交保留恢复所需的数据 | 保留回执旁路、活动与恢复顺序、删除清理和来源版本。体积限制承担完整性保护 |
| 仍有消费者的历史兼容 | 旧库可能带有嵌入的修订、旧格式回执和自动进入 `stale` 的条目。曾经手动暂停的条目也可能处于旧状态 | 保留旧格式读取、修订转存和可续迁移。只恢复带旧自动降级原因且无人工暂停证据的条目。旧视图入口继续打开待整理 |
| 已无决策消费者的统计 | `a8c6cd69` 为「近六个月已提供至少五次但从未获得正向反馈」自动降级而维护 `exposures` 和 `helpful_at`。`9ce1190a` 撤掉了该策略 | 宁可保留效果未知，也不根据沉默降级。本版删除这两项统计的维护与回读，普通召回和 Agent 自报跳过继续留审计记录 |
| 旧健康摘要的重复计算 | `a8c6cd69` 的健康摘要与 `9ce1190a` 新增的待整理队列各自归一化同一批内容，详情查伙伴时又做一遍。来源核验还会为每条关系重建条目查找表 | 本版以一次分组计算复核数量、待整理行和重复伙伴，使用一个 ID 查找表检查来源。来源变化仍列入待整理，页脚告警仍由重复、需复审和反复不适用触发 |

两处看起来重复的代码有实际消费者。构建时的工具清单负责扩展命名和审批，记忆实例随主会话隔离，组装工厂负责创建新实例。双运行时测试会用同一配方打开两次，要求每边只有一个 `recall_memory`，各自只接受自己的对话引文。子 Agent 和工作流使用 `ChildRecipe`。保留这条边界能防止共享工具顺带带入用户记忆。 [运行时隔离回归](../../tests/orchestration/invoker/test_runtime_recipes.py)

主库和旁路中的同类字段也有恢复用途。目录提交先固定条目和恢复信息，再替换回执与补写活动日志。回执旧于目录时从目录恢复，回执新于目录时要求匹配的库文件。把副本一律去重会改变中断后保留什么。初版的 500 条和 8 MiB 已在 `a8c6cd69` 演变成 64 MiB 完整性限制，当前每次和每回合的注入预算继续限制模型看见的内容。

## 这次改动的兼容证据

- `MemoryUse` 保留按版本、回合和情境记录的用户跳过、排除情境与纠正会话。正向反馈仍能解除对应的情境排除。后续提醒与复盘仍能使用纠正证据。
- 读取旧回执或回执缺失时的主库恢复数据，允许旧 `exposures` 和 `helpful_at` 字段存在。下一次正常写入会舍去这些字段，旧来源、回执、活动和当前有效反馈可继续核对。未绑定情境的旧跳过仅保留活动记录。
- 待整理的重复分组仍同时受工作区、记忆类型和归一化正文约束。三条相同内容在队列中显示三个可操作的条目，在健康摘要中计作两项重复。来源变化不会让普通页脚入口改道。
- 服务测试通过真实临时库分别验证旧旁路和主库恢复、普通召回与 Agent 跳过的日志、情境排除及用户反馈恢复。TUI 测试覆盖队列成员、重复伙伴和页脚导航。写入入口的引擎测试覆盖读取资料、生成文档、保存经验和跨会话召回。
- 用两个独立的临时库各保存 24 条合成条目，再用 24 个回合各按 ID 查询一条且不给反馈。两个版本都记录了 24 次提供事件，并保留最后一回合的回执。旁路的 `uses` 从 24 条减为 0 条，文件从 28,452 字节减为 21,648 字节。这个对照只测量这批输入的持久化开销。
